# app

The user-facing mobile application component of Kommunal App, built
with [Flutter](https://flutter.dev/).

## Getting started

1. [Install Flutter](https://docs.flutter.dev/get-started/install) on your system
2. Run `flutter pub get` to install dependencies
3. Set up your preferred IDE for development, or use `flutter run` in the CLI
   (requires a physical device or a running emulator)

We recommend [Android Studio](https://developer.android.com/studio) as a feature-rich Flutter IDE.

## Dev console

During development you can access the dev console in the running app via the menu. This will allow
you, for example, to set the backend URL and the Kommune for which the app is deployed.

If you're running services locally and want to expose them to the app, you can do so using `adb`.
For example, if the backend is running on port 5000, use the following command:

```shell
adb reverse tcp:5000 tcp:5000
```

Then set the backend URL to `http://localhost:5000`. Your changes will persist across restarts.

## Derry scripts

You can install `derry`, a simple script runner, to execute scripts defined in `pubspec.yaml`.

```shell
dart pub global activate derry
```

This is purely for convenience, the scripts are also executable by hand.

## Flutter versions and `fvm`

This project can benefit from [`fvm`](https://fvm.app/docs/getting_started/installation) being
installed on your system. `fvm` allows you to keep multiple isolated versions of Flutter and
selects the correct version on a project-by-project basis.

Use `fvm use` to install and link the version of Flutter SDK specified in `.fvm/fvm_config.json`,
which may be different from your globally installed version. Then, use the proxy commands
`fvm flutter` and `fvm dart` instead of `flutter` and `dart`.

You should exclude the `.fvm` directory in your IDE, to prevent the linked Flutter SDK from being
indexed like regular source files. Furthermore, you can set up Android Studio to use the linked SDK
by going to "Languages & Frameworks > Flutter" and changing the "Flutter SDK Path" setting to
the project-local `.fvm/flutter_sdk` directory.

## Code generation

This project uses `build_runner` for code generation such as GraphQL queries.

Run `derry dev` to run code generation in the background while developing.

## State management / DI

We use [`riverpod`](https://docs-v2.riverpod.dev/docs/concepts/providers) for managing global app
state and dependency injection. The documentation will get you up to speed on how to set up
various types of `Provider`s and read from them using `WidgetRef`s.

## Routing

We use [`go_router`](https://pub.dev/documentation/go_router/latest/index.html) as a routing
solution. There are three shell routes:

- `news`
- `profil`
- `antraege`

These are used to implement nested navigation along with a persistent bottom navigation and main
menu drawer.

## Formatting and linting

Run `derry lint` to auto-format and lint your code. Some fixes, such as adding `const` to variable
declarations, are applied automatically. You can also set up "Format on save" in your IDE. In
Android Studio, this setting is under "Languages & Frameworks > Flutter".

If you're wondering about all the extra trailing commas: this helps the formatter produce [more
readable code](https://docs.flutter.dev/tools/formatting#using-trailing-commas) for deeply nested
structures often seen in widgets.

## Widgetbook

This project uses [Widgetbook](https://www.widgetbook.io/) to create a catalogue of existing widgets
in different variants and states. To launch Widgetbook, run `derry gen` or `derry dev` when working
on the Widgetbook followed by `fvm flutter run -t lib/widgetbook.dart -d <edge|chrome>`. While
targeting the desktop environment would be preferred for development because Widgetbook supports hot
reloads for it, it doesn't play nicely with Firebase (i.e. it doesn't compile).

## Open-source licenses

The profile's Open Source catalogue reads bundled metadata generated by
`dart_pubspec_licenses` from `pubspec.lock`, including transitive dependencies.
It works offline on Android and iOS. Commit `assets/licenses/packages.json`
after dependency changes so direct IDE runs also have current attribution data.

Use the build wrapper for local and CI builds; it resolves dependencies and
regenerates the catalogue before invoking Flutter, stopping if generation fails:

```shell
bash tool/build_with_licenses.sh appbundle --release
bash tool/build_with_licenses.sh ios --release --no-codesign
```

All additional Flutter build arguments (including flavors) are forwarded. CI jobs
that invoke Flutter directly must run this before their build or Xcode step:

```shell
fvm dart run dart_pubspec_licenses:generate --json --ignore app -o assets/licenses/packages.json
```

To regenerate without building, run that same command after `fvm flutter pub get`.
License notices are preserved verbatim. Packages without a supplied license remain
visible and show a localized missing-license notice; inspect these before release.
This catalogue covers Dart/Flutter dependencies, not a native Gradle/CocoaPods audit.
